## 1. 设计原则

AI Workbench 作为平台去管理它名下的各个项目时，遵循以下核心原则：

1. **平台做编排与追溯，不重复造轮子**：代码、文件等资产放在最适合它的存储系统里，平台只持有"元数据 + 引用 + 关联关系"。
2. **每类资产用最合适的存储**：不把代码/大文件塞进数据库，也不自建 Git。
3. **可追溯是第一价值**：需求 → 任务 → 提交/PR → 测试 → 发布 → 线上状态的完整链路是平台区别于割裂工具的护城河。
4. **AI 原生**：平台各模块产生的内容自动沉淀进知识库，成为各场景 AI 能力的统一上下文（RAG）。

## 2. 项目资产管理总览

```
                    ┌─────────────────────────────────────┐
                    │      AI Workbench (PostgreSQL)        │
                    │   Project + Artifact + Relation 表    │
                    │      —— 只存元数据、引用、关联 ——      │
                    └──────────────┬──────────────────────┘
            ┌──────────────┬───────┼────────────┬──────────────┐
            ▼              ▼       ▼            ▼              ▼
       外部 Git         OSS    PostgreSQL    ES + 向量        流水线引擎
   (GitHub/GitLab)    (文件型) (结构化交付物) (知识库 RAG)   (GitHub Actions)
    代码/发布脚本      设计稿   需求/PRD/用例   AI 弹药库       发布执行
```

### 2.1 分资产类型的存储策略

| 资产类型 | 物理存储 | 平台内存储（元数据） | 技术栈 |
|---------|---------|---------------------|--------|
| **代码** | 外部 Git 平台 | repo URL、分支、commit SHA、PR 号 | GitHub/GitLab API + Webhook |
| **发布脚本 / 流水线定义** | 随代码进 Git（脚本即代码） | 流水线引用、执行记录、审批流状态 | GitHub Actions |
| **结构化交付物**（需求/PRD/测试用例） | PostgreSQL，带版本快照 | 实体记录本身 + 版本历史 | PostgreSQL + MyBatis-Plus |
| **文件型交付物**（原型图、设计稿、构建产物、报告） | 阿里云 OSS | object key、版本、大小、关联对象 | OSS |
| **知识库** | 原文入 DB + ES 全文索引 + 向量 | 文档记录、标签、embedding | Elasticsearch 8.x（含向量） |

**关键约束**：
- 代码绝不进数据库。Monaco 在线编辑器（M7）是浏览/轻量编辑，提交仍落到 Git。
- 大文件不进 Git、不进 DB，统一走 OSS。
- 发布脚本属于"脚本即代码"，跟随仓库版本；运行时状态（谁审批、何时发、结果）进 DB。

## 3. 代码托管：只对接外部 Git

> **架构决策（已锁定）**：平台**不自建 Git 服务**，仅对接外部 Git 平台（GitHub/GitLab）。

### 3.1 集成方式

- **授权**：优先使用 **GitHub App**（权限粒度细、体验好），OAuth App 作为备选。
- **数据同步**：通过 **Webhook** 接收 `push`、`pull_request`、`release` 等事件，实时更新平台内的追溯关系与元数据。
- **代码访问**：通过 Git 平台 REST/GraphQL API 拉取文件、提交、PR 信息，供 M7 在线浏览与代码审查使用。

### 3.2 平台内代码相关元数据

```
git_repository {
  id, project_id,
  provider,        // github | gitlab
  repo_url,
  default_branch,
  install_id,      // GitHub App 安装 ID
  ...
}
```

### 3.3 取舍说明

- ✅ 不背 Git 运维负担，M7（代码开发）工作量集中在"对接 + 同步 + 展示"，可控。
- ⚠️ 用户需自带 Git 平台账号与仓库。
- 🔮 后续如需"数据自主可控"，可演进为可配置的内置 Git（如 Gitea），但非 MVP 范围。

## 4. 结构化交付物与文件型交付物

### 4.1 结构化交付物（PostgreSQL）

需求、PRD、测试用例这类**有结构、要评审、要 diff** 的内容：
- 主表 + `xxx_version` 快照表，每次变更存一版，支持回溯与 diff（对应 M4 变更追踪）。
- 评审流程以状态机形式落库。

### 4.2 文件型交付物（OSS）

设计稿、原型导出、构建产物、测试报告等二进制文件：
- OSS 存文件，DB 存 `{ object_key, version, 关联的 project / 需求 / 发布单 }`。

## 5. 知识库：AI 的 RAG 检索源

> **架构决策（已锁定）**：知识库做成**向量化的 RAG 检索源**，作为各场景 AI 能力的统一上下文。

### 5.1 数据流

```
知识来源（自动汇入）          处理管道                 消费方
─────────────────          ──────────              ──────────
需求 / PRD / 文档      ┐                          ┌ M12 AI 助手对话
代码 / PR / CR 记录    ├─→ 分块 chunk            ├ M4  需求分析 AI
测试用例 / 缺陷        ├─→ embedding 向量化  ─→  ├ M7  代码审查 AI
运维日志 / 告警        ┘    ↓                     ├ M8  测试生成 AI
                          ES（全文）+ 向量（语义）  └ M10 日志诊断 AI
```

### 5.2 关键设计

- **自动沉淀**：知识库不是手工录入的孤岛，而是把平台各模块产生的内容（需求、评审意见、缺陷、日志）自动汇入，成为 AI 的上下文弹药。
- **混合检索**：ES 关键词检索 + 向量语义检索，召回效果优于单一方式。
- **向量库选型**：MVP 直接使用 **Elasticsearch 8.x 自带的 dense_vector**，避免额外引入组件；数据量增大后再评估迁移至 Milvus 等专用向量库。

## 6. 全链路追溯模型

平台真正的价值在于这张**追溯关系图**，通过一张通用关系表实现跨模块连接。

### 6.1 统一抽象

```
Project（项目）
  ├── 关联一个 / 多个 Git Repository（引用）
  ├── 拥有多种 Artifact：
  │     artifact {
  │       id, project_id, type, storage_backend,
  │       uri / object_key, version, created_by, ...
  │     }
  │     type            ∈ { 需求, 设计稿, 文档, 构建产物, 发布脚本, 知识条目, ... }
  │     storage_backend ∈ { DB, OSS, GIT, ES }
  └── 关联关系表（追溯图核心）：
        relation {
          from_type, from_id,
          to_type,   to_id,
          relation_kind   // 实现 | 验证 | 发布于 | 部署到 | ...
        }
```

### 6.2 追溯链示例

```
需求#12 ─实现→ PR#45 ─验证→ 用例#8 ─发布于→ 发布单#3 ─部署到→ 环境:prod
```

### 6.3 价值

- 新增资产类型 = 加一个 `type` + 选一个 `storage_backend`，不改架构。
- 追溯图即对 `relation` 表的图遍历，前端可渲染"需求全生命周期视图"——这是平台区别于割裂工具链的护城河。

## 7. 对话式编排层（Chat 入口）

> **架构决策（已锁定）**：平台主入口为 **Chat + 工作台双栏** 的对话式界面；背后采用 **多专家 Agent（按 SDLC 阶段划分）** 拓扑。

chat 入口不是一个聊天框，而是平台的**对话式编排层**：用户用自然语言驱动，背后由 Agent 调度全平台能力，完成"创建项目 → 沟通需求 → 修改代码 → 发布"等 SDLC 全链路动作。这是"AI 原生"主张的落地核心。

### 7.1 交互形态：Chat + 工作台双栏

```
┌────────────────────────┬──────────────────────────────┐
│   左：对话区(驱动)        │   右：工作台(产物 / 动作预览)    │
│                        │                              │
│  用户: 给项目X加登录页    │  ┌── 需求表 ──┐  ┌── 代码diff ──┐ │
│  Agent: 已起草需求…→     │  │ 需求#12     │  │ +登录组件     │ │
│  Agent: 生成代码diff…→   │  └────────────┘  └─[确认/拒绝]─┘ │
│  [流式回话]              │  ┌── 发布状态 ──────────────┐    │
│                        │  │ 发布单#3  待审批          │    │
└────────────────────────┴──────────────────────────────┘
```

- 左侧对话流式驱动；右侧实时渲染被操作的产物（需求表、代码 diff、发布状态）。
- 高风险动作在右侧生成**预览 / diff**，用户确认后才执行（体验类似 Cursor / Claude Code）。
- 复用 M1-M11 的页面组件作为右侧"产物视图"，避免重复造 UI。

### 7.2 多专家 Agent 拓扑

```
                用户(自然语言对话)
                       │
              ┌────────▼─────────┐
              │  编排 / 路由 Agent  │  意图识别·任务规划·上下文管理·汇总回话
              └────────┬─────────┘
        ┌──────┬───────┼────────┬────────┐
        ▼      ▼       ▼        ▼        ▼
    项目Agent 需求Agent 代码Agent 测试Agent 发布Agent
     (M3)     (M4)    (M7)     (M8)     (M9)
        │      │       │        │        │
        └──────┴───工具集 = 各模块 API────┴───────┘
                       │
          共享上下文：RAG 知识库 + 当前项目状态
```

- **编排 / 路由 Agent**：理解意图、拆解任务、分派给专家、汇总结果回话，并维护对话上下文。
- **专家 Agent**：每个对应一个 SDLC 阶段，持有该阶段模块的 API 工具集与领域提示词。
- 跨阶段任务（如"实现需求#12 并提测"）由编排 Agent 串联多个专家依次执行。

### 7.3 工具 = 平台模块 API

Agent **不直接操作数据库 / Git**，而是调用平台已有的、带权限校验的业务 API（tool use / function calling）：

| 专家 Agent | 工具示例（平台 API） | 对应模块 |
|-----------|---------------------|---------|
| 项目 Agent | `createProject` / `addMember` | M3 |
| 需求 Agent | `createRequirement` / `analyzeRequirement` | M4 |
| 代码 Agent | `getFile` / `proposeCodeChange` / `createPR` | M7（经外部 Git API） |
| 测试 Agent | `generateTestCase` / `runTestPlan` | M8 |
| 发布 Agent | `triggerPipeline` / `submitReleaseApproval` | M9 |

安全边界天然复用 M2 的 RBAC——Agent 能做什么，取决于当前操作人的权限。

### 7.4 上下文与状态

- **领域上下文**：从 RAG 知识库（第 5 章）检索该项目的需求、代码、历史，作为 Agent 的上下文弹药。
- **会话状态**：多轮对话、当前聚焦的项目 / 需求、待确认动作等以会话维度持久化。
- **当前项目状态**：实时项目元数据（成员、仓库、进行中的发布单）随上下文注入。

### 7.5 人在回路与风险分级

对话驱动不能变成黑盒操作，高风险动作必须经人确认：

| 风险等级 | 例子 | 策略 |
|---------|------|------|
| 只读 / 查询 | 看需求、查状态、搜知识库 | Agent 直接执行 |
| 低风险写 | 建项目、记需求、建任务 | 执行后告知，可撤销 |
| **高风险写** | 改代码并提交、触发生产发布 | **右侧生成预览 / diff，确认后执行**；大动作走 M9 审批流 |

### 7.6 对话动作的追溯

每个由对话触发的动作都写入 `relation` 表（第 6 章），记录"谁通过对话创建 / 修改 / 发布了什么"，使对话操作同样进入全链路追溯图，可审计、可回溯。

### 7.7 技术实现要点

- **流式回话**：SSE 或 WebSocket 推送 Agent 的思考与动作进度，左侧实时呈现。
- **双栏联动**：Agent 动作通过事件驱动右侧工作台刷新对应产物视图。
- **AI 模型**：经 M12 的多模型可插拔层调用（OpenAI / Claude / Gemini），编排与专家可按需用不同模型。
