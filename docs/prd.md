# AI Workbench — 产品需求文档（PRD）

> **版本**: v0.1
> **日期**: 2026-06-04
> **负责人**: Jason
> **状态**: 草稿（首版聚焦核心差异化能力：对话式编排入口 + 全链路追溯；各模块逐步细化）

---

## 1. 文档说明

本文档定义 AI Workbench 的功能需求、用户故事与验收标准。功能模块编号沿用 [project-plan.md](./project-plan.md) 第 4 节（M1–M12），技术实现见 [system-architecture.md](./system-architecture.md)。

- **用户故事**格式：`作为 <角色>，我希望 <目标>，以便 <价值>`。
- **验收标准（AC）**采用 Given / When / Then，可直接转测试用例。

---

## 2. 目标用户与角色

| 角色 | 画像 | 核心诉求 |
|------|------|---------|
| 项目负责人 / PM | 管理项目、需求、进度 | 一处掌控全链路、需求到上线可追溯 |
| 研发工程师 | 写代码、提 PR、改 Bug | 减少工具切换、AI 辅助编码与审查 |
| 测试工程师 | 设计/执行用例 | AI 生成用例、执行记录可追溯到需求 |
| 运维工程师 | 发布、监控、排障 | 一键发布、日志聚合、AI 诊断 |
| 平台管理员 | 组织/权限配置 | RBAC、成员与项目治理 |

权限模型对应 M2（RBAC）；**Agent 能执行的动作受当前用户权限约束**（架构 7.3）。

---

## 3. 产品范围与优先级

模块与优先级见 [project-plan.md](./project-plan.md) 第 4 节。本 PRD 详述 P0 与对话式编排相关需求，其余模块给出关键故事，细节随里程碑补充。

**核心差异化（贯穿全产品）**：
1. **对话式编排入口**（M12）—— 用自然语言驱动 SDLC 全流程。
2. **全链路追溯** —— 需求 → 代码 → 测试 → 发布 → 线上，含对话动作。
3. **AI 原生** —— 各环节内嵌 AI，知识库做 RAG 上下文源。

---

## 4. 核心场景：一句话驱动 SDLC

> **场景串联**：PM 在 chat 里说"给项目X加一个登录页"，平台依次：起草需求 → 生成代码变更（待确认）→ 用户确认后提 PR → 生成测试用例 → 发起发布，全程产物在右侧工作台可见、动作可追溯。

此场景贯穿 §5 的 M12 / M3 / M4 / M7 / M8 / M9 用户故事，是 MVP 的验收主线。

## 5. 功能需求详述

### 5.1 M12 对话式编排入口（P0，核心）

#### US-12.1 双栏对话工作台
**作为** 操作人员，**我希望** 在"左对话 / 右工作台"的界面里用自然语言操作，**以便** 对话与产物可视化结合。

**AC：**
- Given 已登录用户进入工作台，When 发送消息，Then 左侧以**流式**逐字呈现 Agent 回复（SSE，对应 [api-design.md](./api-design.md) §3）。
- Given Agent 产生/修改了产物（需求、代码 diff、发布单），When 收到 `artifact.updated` 事件，Then 右侧工作台**实时刷新**对应产物视图。
- Given 网络断开，When 重连，Then 通过续流接口补齐断点后事件，对话不丢失。

#### US-12.2 多专家 Agent 协作
**作为** 操作人员，**我希望** 系统自动把我的请求分派给合适的专家（需求/代码/测试/发布），**以便** 我无需关心内部分工。

**AC：**
- Given 一句跨阶段请求（"实现需求#12 并提测"），When 处理，Then 编排 Agent 依次分派多个专家，左侧通过 `agent.dispatch` 显示当前专家。
- Given 某专家执行失败，Then 回复中说明失败原因，且不影响已成功步骤的产物。

#### US-12.3 风险分级与动作确认（Human-in-the-loop）
**作为** 操作人员，**我希望** 高风险操作（改代码、发布）先预览再确认，**以便** 避免误操作。

**AC：**
- Given 只读/低风险动作，When 触发，Then Agent 直接执行并告知结果（低风险可撤销）。
- Given 高风险动作（`high_write`），When Agent 提出，Then 流以 `action.proposed` 暂停（`awaiting_confirm`），右侧显示 **diff/预览** 与 `[确认]/[拒绝]`。
- Given 待确认动作，When 无权限用户尝试确认，Then 返回 403，动作保持 `pending`。
- Given 用户点击确认，When 执行，Then 通过确认接口（[api-design.md](./api-design.md) §4.3）流式返回执行结果，状态机 `pending→confirmed→executing→succeeded/failed`。
- Given 用户拒绝，Then 动作 `rejected`，不产生任何副作用。

#### US-12.4 知识库 RAG 上下文
**作为** 操作人员，**我希望** Agent 了解当前项目的需求/代码/历史，**以便** 回答与操作贴合项目实际。

**AC：**
- Given 已绑定项目的会话，When Agent 处理请求，Then 检索该项目知识库（ES 全文 + 向量）作为上下文。
- Given 平台各模块产生新内容（需求、CR、缺陷、日志），Then 自动汇入知识库可被后续检索。

#### US-12.5 对话动作可追溯
**作为** PM，**我希望** 每个由对话产生的操作都被记录，**以便** 审计"谁通过对话做了什么"。

**AC：**
- Given 任一 Agent 动作执行完成，Then 写入 `relation` 表（`from_type=agent_action`），并通过 `agent_action_artifact` 关联受影响产物。
- Given 查看某需求/发布单，Then 可回溯到产生它的对话动作与操作人。

### 5.2 M3 项目管理（P0）

#### US-3.1 对话/页面创建项目
**作为** PM，**我希望** 通过对话或页面创建项目并绑定 Git 仓库，**以便** 快速开工。

**AC：**
- Given "建个项目叫 X，仓库是 github.com/a/b"，When 处理，Then 创建 `project` 记录并通过外部 Git 授权绑定 `git_repository`（架构第 3 章）。
- Given 项目创建成功，Then 右侧展示项目卡片，创建动作进入追溯图。

#### US-3.2 成员与配置
**作为** PM，**我希望** 管理项目成员与角色，**以便** 控制访问。
**AC：** 成员增删改、角色分配生效，越权访问被拒（RBAC）。

---

### 5.3 M4 需求管理（P0）

#### US-4.1 AI 起草与采集需求
**作为** PM，**我希望** 口述意图后 AI 起草结构化需求，**以便** 减少撰写成本。
**AC：**
- Given 自然语言意图，When 处理，Then 生成结构化需求（标题/描述/验收标准）并落 `artifact(type=需求)`，存版本快照。
- Given 需求生成，Then 右侧可编辑，确认后入库。

#### US-4.2 评审与变更追踪
**作为** PM，**我希望** 需求走评审、变更留痕，**以便** 可追溯。
**AC：** 评审状态机生效；每次变更产生新版本，可 diff 历史。

---

### 5.4 M7 代码开发（P1）

#### US-7.1 AI 提出代码变更（高风险，需确认）
**作为** 研发，**我希望** 描述需求后 AI 生成代码变更供我确认，**以便** 加速实现。
**AC：**
- Given 代码变更请求，When Agent 处理，Then 产出 `proposeCodeChange`（`high_write`）含 diff 预览。
- Given 用户确认，Then 经外部 Git API 创建分支/PR，结果含 `pr_url`，产物追溯到需求。

#### US-7.2 在线浏览与代码审查
**作为** 研发，**我希望** 在线查看代码并做 CR，**以便** 不切工具。
**AC：** Monaco 浏览/轻量编辑；CR 评论与 AI 审查意见可关联到 PR。

---

### 5.5 M8 测试管理（P1）

#### US-8.1 AI 生成用例
**作为** 测试，**我希望** 基于需求自动生成用例，**以便** 提效。
**AC：** 用例关联来源需求；执行记录可追溯到需求与发布。

---

### 5.6 M9 发布管理（P1）

#### US-9.1 触发发布（高风险，需审批）
**作为** 运维，**我希望** 通过对话或页面触发发布并走审批，**以便** 安全上线。
**AC：**
- Given 触发生产发布（`high_write`），Then 生成发布单 `pending`，走审批流后才执行流水线（GitHub Actions）。
- Given 发布完成，Then 发布单关联到对应 PR/版本/环境，进入追溯图。

## 6. 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | SSE 首字节 < 1s；会话历史分页加载；高频"待确认动作"查询走部分索引。 |
| 安全 | JWT 鉴权；动作执行二次校验 RBAC；高风险动作必须人工确认；操作全程审计。 |
| 可靠性 | SSE 断线可续流；动作"提出-确认-执行"跨请求，对断线/超时/多端鲁棒。 |
| 可扩展 | 新增 Agent 动作类型不改表结构（`params/result` 用 JSONB）；新增资产类型仅加 `type`。 |
| 可观测 | 记录每次模型调用的 token/延迟（`message.meta`）。 |
| AI 成本/可用 | 多模型可插拔 + 降级 + 限流（plan 第 7 节风险对策）。 |

## 7. MVP 范围与验收主线

**MVP 必须打通 §4 核心场景**：对话创建项目 → AI 起草需求（确认入库）→ AI 提代码变更（确认提 PR）→ 全程产物在右侧可见、动作可追溯。

对应模块 MVP 子集：M2（认证/RBAC）、M3、M4、M7（提变更+确认）、M12（双栏+多专家+确认+RAG），其余按里程碑（plan 第 5 节）推进。
